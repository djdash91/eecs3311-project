# Design changes (Stage 2, section 11)

Format required by the project: original design, change, reason.

## Decisions made by the starter code

These came with the starter code, not from you. For each one, decide whether to keep it, change it or revert it, and edit the reason into your own words. The marker will expect you to explain them.

| Original design (Stage 1) | Change | Reason |
|---|---|---|
| `Tool` has only `execute(input, session)` | Added `name()`, `description()` and `inputSchema()` | Claude needs a name, a description and a JSON schema for every tool. |
| `FixCommand` has `execute` and `undo` | Added `issueId()` and `description()` | Undo, the report and the Audit's history need to know which issue each fix addressed. |
| `Rule` has `id()` and `check()` | Added `criterion()` | Each issue records its WCAG criterion, and the rule is the one place that knows it. |
| `AgentSession` holds messages, mode, running flag and pending proposal | Added `pendingToolUseId` and held tool results | SD05 says the decision becomes the result of the waiting tool call, and other results from the same turn are sent with it. The session must remember which call that was. |
| `FixProposal` holds "its values" | One `value` string | Every fix type takes exactly one value (alt text, label, aria-label, language or title). |
| `AuditRepository.findById` returns `Audit` | Returns `Optional<Audit>` | Makes "not found" explicit; the facade turns it into NotFoundException. |
| `IssueAssistant.suggestAltText` returns `String` | Returns `Optional<String>` | "No suggestion" is a normal outcome in F07 (no screenshot, API failure, failed checks). |
| One `AuditRepository` backed by H2 | Two implementations chosen by `accessfix.storage` | Unit tests and early development need storage before the H2 version exists. |
| `submitDecision(auditId, decision)` | `submitDecision(auditId, approved, reason)` | The proposal lives in the session, so the facade builds the Decision. |
| Rule IDs not specified | Constants in `RuleIds` | Issue IDs, FixType and prompts all refer to them. |
| `ToolResult` holds output or an error | Status of OK, ERROR, PENDING or ACCEPTED, plus an optional payload | Fix mode needs "pending" (SD05) and Plan mode needs "accepted" (SD04). |

## Your changes during implementation

| Original design | Change | Reason |
|---|---|---|
| F02 says each rule checks one WCAG criterion, but doesn't name them | `form-label` and `button-name` check 4.1.2 (Name, Role, Value); `link-name` checks 2.4.4 (Link Purpose (In Context)); `page-lang` checks 3.1.1 (Language of Page); `page-title` checks 2.4.2 (Page Titled) | Each rule needs one criterion for its issues and for F03 explanations. All three are in `wcag-criteria.json` (F05). |
| F02 doesn't say which elements each rule checks | Each element is checked by one rule: form fields (`input`, `select`, `textarea`) belong to their type, and any other element belongs to its role. So `input type=button` and `type=image` are checked by `ButtonNameRule`, not `FormLabelRule`; a text input with `role="button"` stays with `FormLabelRule`; `<a href role="button">` goes to `ButtonNameRule`; and `<button role="link">` goes to `LinkNameRule` | One element is reported by one rule, so issue counts, plans and the report don't count the same problem twice. A form field's name comes from its label, value or alt whatever its role, while other elements take their name from their content, so this split also checks each element the right way. |
| F08 says adding a label fixes an unlabelled field, and Task 4 says rules skip hidden elements | `FormLabelRule` doesn't count a label the snapshot records as hidden | A hidden label doesn't help users, and F08's fix adds a visible one. Links and buttons also ignore hidden content. |
| Task 4 (F02) says rules skip the elements the snapshot records as hidden | `PageTitleRule` doesn't skip hidden elements; its issue always points at the head element | Browsers never display the head, so SnapshotService's visibility check records it as hidden, and the rule would never report a missing title. The title is still read out and shown in the tab, so it must be checked. |
| F01 says SnapshotService gives every element a stable ID when the page loads | Fixes that add an element give it a stable ID: `AddLabelFix` uses the field's plus "-label" (for example `e7-label`), and `SetTitleFix` uses the head's plus "-title". `AddLabelFix` also gives the field an `id` ("af-" plus its stable ID) if it has none | Added elements didn't exist at load time, so they have no stable ID. Undo needs one to remove exactly that element, and the `label[for]` needs an `id` to point at. The "-label" and "-title" forms can't clash with SnapshotService's IDs, which are always "e" plus a number ("e0", "e1"...); `SnapshotServiceTest` checks this form. |
| SD06: if the fix type isn't allowed or the issue isn't in the latest scan, "the refusal is the result that goes back to the agent and the User" | `FixService.applyVerified` refuses by throwing `InvalidInputException` (HTTP 400) before the page changes, instead of returning a rolled-back `VerificationResult` | SD06 records a failed fix only when an applied fix fails verification. A distinct exception lets `ApprovalGate` return the refusal to the agent as an error result without counting it towards the retry limit of two failed fixes. |
| SD05: `FixService.preview` returns "the affected code before and after", without saying which code | `preview` returns the smallest part of the page the fix changed, as "Before:" and "After:" text, without stable IDs. For an attribute fix that's the element; for an added label or title it's only the added and changed nodes | F08 shows each proposal as a before-and-after diff. Showing the whole parent (a form or a long head) would hide the change, and the same issue snippets are shortened to 300 characters. |
| SD05: `ProposeFixTool` refuses disallowed fixes before `ApprovalGate` calls `preview` | `preview` also refuses, by throwing `InvalidInputException`, a fix that `applyVerified` would refuse or that can't be applied | The user should never be shown a diff for a fix that would be refused when they approve it. Both methods share one check, so they always agree. |
| F01: hidden elements are recorded "as Playwright reports them after rendering the page" | `SnapshotService` uses the browser's `checkVisibility` with the `visibility` check, as the starter suggests: an element is hidden if it or a parent has `display: none`, or it has `visibility: hidden`. Playwright's own visibility test would also call zero-size elements hidden; this doesn't | Screen readers skip `display: none` and `visibility: hidden` content, but still read zero-size content, so treating zero-size elements as hidden would make rules miss real issues. |
| F01: a screenshot of "each image that has no alt text" | Only images with no `alt` attribute that are visible, have a size and loaded get a screenshot | `alt=""` marks a decorative image, which isn't an issue. A hidden, zero-size or broken image can't be photographed; F07 already says a broken image has no screenshot and the user writes the alt text. |
| F01 / UC01 2a: "site can't be reached, or times out" is an error | An HTTP error status (400 or higher, such as 404) is also a `PageLoadException` | The browser can render an error page, but scanning it would audit the server's error page, not the page the user asked for. |
| F01 / UC01 1a: "Invalid URL: an error is shown", without saying what counts as valid | `AccessFixFacade.loadPage` accepts only `http` and `https` URLs with a host, such as `https://example.com`. Anything else, including `file:`, `javascript:` and addresses without `https://`, is refused with `InvalidInputException` before Playwright starts | The GUI sends URLs to the server, so a `file:` URL would let anyone with the GUI read files from the server's disk. Uploaded files are loaded with `captureHtml` instead, and the CLI's `load` command already reads a file path as an HTML file. |
| F05: search "matches the query's words against each entry's number, title and summary, and ranks entries by how many words match", and returns "the ranked entries" | Words are compared whole, ignoring case, punctuation, a plural "s", single letters and common words such as "the" and "what". Each query word counts once. Ties keep the data file's order, and at most 5 entries are returned | Without ignoring common words, "what is the page title" would match almost every entry. Without the plural rule, "form labels" wouldn't match "label". Five results are enough for the agent and the search box; more would mostly be weak one-word matches that fill the model's context. |
| View C shows the rules but no shared helper | Added `RuleSupport.hasNameFromContent`, used by `LinkNameRule` and `ButtonNameRule` | Links and buttons get their name from their content in the same way, so the logic is written and tested once. `RuleSupport` itself came with the starter. |
| Stage 1 lists an H2 database for storage and `AuditRepository` "stores audits", but doesn't say how | `JdbcAuditRepository` stores each audit as one row: its ID and the whole `Audit` as JSON (`schema.sql`). The JSON is read from and written to fields, so each applied fix keeps its undo information, and each fix is stored with its `FixType` name, such as `"type": "SET_ALT_TEXT"`. The JSON settings are in the repository, not on the domain classes; each fix class gained a `protected` constructor "for JSON libraries only", as `Audit` already had. Storage is now `h2` by default | An audit is always loaded and saved whole, so one JSON row is simpler than a table per class. Undo must still work after a restart or in a later CLI command (F09, F11), which needs each fix's old value, not just the new one. `FixType` names stay the same if a class is renamed. Keeping the JSON settings in the repository means the core doesn't depend on how it is stored (view C). |
| F10: the report contains the first and latest issue counts, the verified fixes, the escalated issues and a note on automated checks; UC10 1a: with no fixes it "shows the starting issues" | The report always lists the issues in the latest scan, and adds a count for each rule, a warning when a rule didn't run, and whether each escalated issue is still found. Fixes are listed in the order they were applied, and escalated issues by ID | Listing the latest scan's issues covers UC10 1a without a separate layout: with no fixes, the latest scan has the starting issues. A count is only meaningful if the reader knows which rules ran. Fixed orders make the report the same every time it is exported for the same audit. |
| `ContentBlock` has text, tool use, tool result and image blocks | Added `Thinking` and `RedactedThinking` blocks. `ClaudeLLMClient` returns them, and sends them back unchanged in later turns. Every request also turns on the API's server-side fallback for declined requests | The model (Claude Opus 5.5) always thinks, and the API rejects a conversation whose earlier thinking blocks were changed or dropped. Keeping them as AccessFix types keeps the SDK inside the adapter. The fallback means a declined request is retried on another model rather than failing. |
| F07: the model "suggests one alt text" | `IssueAssistant` asks for it as a small `AltTextSuggestion` record (structured outputs), with the page title and the nearest text around the image as context | A record gives exactly one alt text, with no extra wording to strip off. The page text tells the model what the image is for. |
| The AI model is Claude Opus 5.5, called through the Anthropic Java SDK (`ClaudeLLMClient` adapts `AnthropicClient`) | Added a second adapter, `GeminiLLMClient`, for Google's Gemini (`gemini-3.5-flash-lite`, Google AI Studio, Gen AI Java SDK). `accessfix.llm` in `application.properties` chooses between them; Gemini is the default. `ClaudeLLMClient` is kept and works as before | Cost: Google AI Studio has a free tier, which suits a course project. The change shows the Adapter pattern working: only the new class imports Google's SDK, and nothing that uses `LLMClient` changed. Gemini's thought signatures are carried in `ContentBlock.Thinking`, and its stop reasons are translated to the same values Claude's adapter returns, so the agent loop works with either. Each request has a 60-second timeout and at most one retry: the SDK has no timeout by default, and its default retries used up the free tier's daily limit in one test run. |
| SD06: a paused Fix run resumes with the user's decision as the tool result | `AgentController.run(session, null)` means "continue": the facade adds the decision and the held results as one tool-result message, then calls `run` with no new text | The starter's design note offered this option. It keeps one loop for starting and resuming, so the step limit, events and error handling are the same in both. |
| UC04 1c, UC08 *b: when the step limit is reached, "the agent says what it couldn't check" / "shows what is left" | On the run's last step, a note is added to the instructions telling the model to answer without tools and say what it couldn't check. Tool calls it makes anyway aren't run; they get a "Not run" error result | The agent can only say what it couldn't check if it is asked before the limit, without using an extra call. Answering every tool call keeps the conversation valid for the next question. |
| `AgentSession` holds the conversation | Added `addUserContent`, which joins user content to the last message when that is already a user message | A run can end with tool results as the last message (a plan accepted, the step limit). The next question then belongs in the same turn, because the models expect user and model turns to alternate. |
| SD03: if the API fails, "the run stops with an error" | `AgentController` publishes an ERROR event, then lets the `LLMException` reach the facade; the audit stops being busy | The GUI's agent panel learns about the error from the same event stream as the progress, and can show it with Retry (UC04 1d). |
| `ToolRegistry` "validates the input" | Checks the top level of the tool's JSON Schema: required fields, types and enum values. A whole number sent as 2.0 counts as an integer | Models sometimes send numbers as decimals (JSON has one number type). Nested fields are left to each tool, which already returns its own error results. |
| `inspect_element` returns an element's code and, for an image, its screenshot; tool results are text | `ContentBlock.ToolResultBlock` has an optional `image`. `InspectElementTool` returns the screenshot as its result's payload, and `AgentController` puts it in the tool result. Both adapters send it: Claude as an image block in the tool result, Gemini as a part of the function response | The starter's design question. The model needs to see the image to write alt text in Fix mode, and both APIs accept an image in a tool result. |
| `MemoryManager.recordEscalation(auditId, issueId)`; `Audit` keeps escalated issue IDs | `recordEscalation(auditId, issueId, reason)`; `Audit` also keeps each escalated issue's reason, and the report shows it | The starter asked where `escalate_to_human`'s reason is stored. The report needs it: a person picking up an escalated issue should know why. Manual plan items and the retry limit give their own reasons. |
| SD04: `PlanMode.onTurnEnd()` stops the run once a valid plan is submitted | It looks at the latest tool results in the session: a `submit_plan` call whose result isn't an error means the plan was accepted | One of the two options the starter offered, and the one Stage 1 describes. The mode needs nothing stored on the session. |
| F06: every issue "exists, appears once and has an allowed fix type" | `RemediationPlan.validate` also requires every issue in the latest scan to appear, priorities of 1 or more (shared priorities allowed) and a reason for every item; "manual" is allowed for any issue | Answers to the starter's open questions. A missing issue would never be fixed or escalated; several issues can be equally urgent; the user approves the plan from its reasons; and the right text can depend on facts only the site owner knows. |
| F08: the agent "shouldn't propose" a rejected fix again | `ProposeFixTool` also refuses a proposal identical to one the user rejected. It gets the retry limit from `ApprovalGate.retryLimit()` | F11 tells the agent about rejections, but a limit like this is enforced in code, as Stage 1 says for the other limits. A different fix for the same issue is still allowed. |
| UC08 step 1: the fix session works through the approved plan | The plan message sent to the agent marks items no longer in the latest scan as "already fixed, skip", as it marks manual items; `FixMode`'s instructions say to skip both | An issue can be fixed after the plan is approved, for example with Suggest alt text and Apply. Without the mark the agent spends steps (and requests) proposing a fix that `ProposeFixTool` then refuses. The refusal stays as the safeguard. |
| SD04: approving a plan has no busy check | `approvePlan` is refused while the audit is busy | The approved plan is what a running fix session works through, so it shouldn't change under it. |
| `AgentSession.clearMessages()`: "Decide when to call it" | Ask follow-ups continue the conversation; asking after another mode, creating a plan and starting a fix session each start a new one. `submitDecision` continues the fix session | Each mode's instructions and tools differ, so mixing conversations would confuse the model, while a follow-up question needs the earlier answer. A new fix session after an API failure starts cleanly (UC08 *a). |
| SD06: the controller publishes "session finished" when a fix session ends | `AgentController` publishes SESSION_FINISHED whenever a run ends without a fix waiting, in every mode | The agent panel needs to know the agent has stopped in Ask and Plan mode too. A run paused for a decision hasn't finished. |
| UC07: the user edits the suggestion, then it is applied and verified | `applyFix` applies the user's text without the F07 checks, and a failed user fix doesn't count towards the agent's retry limit | The checks apply to the model's suggestion (F07 step 2). The user stays in control of their own text, and verification still decides whether the fix is kept. |
| `RestApiController.loadPage(request)` returns an `Audit` | It returns an `AuditSummary` (ID, source and latest scan) | The `Audit` includes the snapshot's HTML and screenshots, and Jackson can't serialise its `FixCommand` objects once fixes exist. The GUI needs only the summary. |
| SD05: `SseEventStream` sends each event to `AgentPanel` | Each event is sent as an SSE event named after its type (`PROGRESS`, `FIX_PROPOSED`, …), with the `AgentEvent` as JSON. A closed tab's `IOException` is rethrown unchecked, so `AgentEventPublisher` removes the stream and the agent carries on | The browser's `EventSource` listens by event name, and a closed tab mustn't stop a run. |
| SD05: the fix proposal reaches `AgentPanel` over the SSE connection | The panel shows the proposal from the `FIX_PROPOSED` event (with its before-and-after code), or from the `AgentResult` if that arrives first; the event then fills in the code | The HTTP response and the event travel on different connections, so either can arrive first. |
| F08: "The Claude API fails: the run stops, verified fixes are kept, and the user can start the session again" | When a request after a decision fails, the panel's Retry starts the session again rather than resending the decision | The decision was already carried out before the model was called, so resending it would be refused ("No fix is waiting for a decision"). |
| Class diagram view A: three separate React views | The views stay mounted and are hidden when not selected; selecting one moves focus to its heading | A fix session and its event stream continue while the user checks the Audit or Reports page, and keyboard and screen reader users start at the new page's content. |
| F07: "the user edits the suggestion and selects Apply" | After Suggest alt text, the field is shown even when no suggestion could be made, so the user writes the text there | UC07's alternative flows say the user writes the alt text when there is no suggestion. |
| Section 1.1: "Plans and fix proposals are approved or rejected at the terminal prompt" | A `TerminalPrompt` class reads the answers: y or n (asked again otherwise), a reason, and alt text. The commands receive it like the facade | Commands that read from `System.in` directly can't be tested; tests give `TerminalPrompt` scripted input. |
| The CLI's `fix` command | The class is `FixSessionCommand` (the command is still `fix`). If the input ends while a fix is waiting, the session stops and verified fixes are kept | `FixCommand` is already the Command pattern's interface. The session lives only in that process, so nothing is left waiting. |
| `ConsoleEventPrinter` receives agent events such as fix proposals | It also prints a proposal's before-and-after code from the FIX_PROPOSED event | The CLI user has to see the change before deciding at the prompt, as the agent panel shows it. |
| The CLI's `alt` command | Shows the suggestion; Enter applies it, typed text replaces it, `cancel` stops. Without a suggestion, the user types the alt text | The terminal version of "edits the suggestion if needed and selects Apply" (F07) and UC07's alternative flows. |
| The CLI's `report` and `export` commands | Print the Markdown or HTML, or save it with `-o file` | Printing lets the output be piped; a file is the terminal's version of a download. |
| The new commands print through picocli's output writer | `load` and `scan` (the starter's worked examples) still use `System.out`; the new commands use `spec.commandLine().getOut()` | Tests can capture the output; both go to the terminal when the app runs. |
